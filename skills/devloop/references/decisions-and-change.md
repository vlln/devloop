# 决策、变更与评审协议

本协议定义新输入、有限授权、范围变更与评审收敛；记录归属见[记录约定](<records.md>)。

## 1. 新输入：先对照承诺，再决定执行

**触发**：用户、协作者或验证结果带来可能改变当前工作的输入。

1. 读取与本输入相关的当前交付承诺、活跃工作和已决边界。无需每个提问都扫描全库。
2. 区分输入的实际效力：提问/探索、澄清、候选改进、缺陷、范围调整、暂停/撤销、明确执行指令。分类服务于行动，不要求向用户逐条展示标签。
3. 对照已有决定与授权，判断可以直接继续、需要影响说明还是需要一个新决定。
4. 范围内且低影响：直接处理，按记录归属更新。只讨论可行性：回答讨论，不自动排期或实现。
5. 显著改变本轮承诺：按第 3 节说明影响并建议处置；用户已有明确选择时直接采用，不能对同一选择反复请示。

**持久化**：仅登记需跨会话跟踪的输入与处置；一次性问答无须制造 backlog。候选可以未定型，但必须与已承诺工作分开。

**结束条件**：本输入被回答、采纳、延期、拒绝、撤回或交给明确的澄清/探索工作；不存在“讨论过所以默认正在实现”的状态。

## 2. 决定与授权：认可已有共识，不扩大许可

### 2.1 三种不同的结论

| 结论 | 含义 | 不能自动推出 |
|---|---|---|
| 需求/范围确认 | 已采纳某项目标或行为 | 当前已排期，或允许生产操作 |
| 技术可接受性 | 方案足以满足用途及适用约束 | 有权改变用户目标、承担预算或执行发布 |
| 执行授权 | 可在指定对象、范围和条件内实施动作 | 同类的所有未来对象、环境与无关副作用 |

一次表达可以同时形成三种结论，但只能按实际内容解释。文档 promote 表示内容被采纳，不是必须额外演示的批准仪式。

### 2.2 复用检查

执行重要决定前，对照：

- 来源：决定来自用户、事项负责人，还是仅是 Agent 的提议？委托是否真实存在？
- 对象：本次要求、工作、版本/候选和环境是否仍被覆盖？授权可覆盖明确的版本集合，不必每次绑定唯一 hash。
- 边界：允许做什么、明确不做什么、预算/数据/外部影响限制是什么？
- 条件：约定验证、观察、审批或恢复条件是否满足？
- 变化：是否有撤回、替代或会改变原取舍的重要新信息？

全部适用则复用，记录必要核对，不重复索要同义批准。只对缺口或变化请求决定；不把整套事项退回从零审批。

“按建议走”按明确被指向的建议解释；“看起来不错”按议题判断可能只是方案认可。生产切换、付费资源、数据删除等动作若仍无可靠覆盖，暂停相关动作并澄清；其他已授权且可独立进行的工作可以继续。低后果细节可说明假设后推进，不能以这种办法扩大外部副作用。

角色名、Agent 层级、审查通过、某状态值和 Agent 自己写入的批准记录均不产生额外权限。平台确认与安全限制仍按实际环境执行，不能用项目文件绕过。

### 2.3 最小记录及失效

重要决定/授权在就近权威记录中保留：内容、来源定位或忠实摘要、对象与边界、条件、关联交付/基线、替代或撤回关系。引用而非复制；不得编造人类签名或不可验证的消息标识。

记录需足够使后续 Agent理解，但不能代替不存在的原授权。无法可靠恢复重要操作许可时，重问该许可，不连带否定无关工作。用户撤回后，停止未来被撤回动作；对已经发生的不可逆影响如实说明并提出恢复选择，不伪称已撤销。

授权失效只影响不再覆盖的部分。时间流逝、文档重排或执行者更换本身不让所有决定失效。新目标、实质风险、候选/环境变化或未满足条件可能使部分授权需要重新判断。

**结束条件**：对将执行的动作，能说明适用决定与授权，或明确等待什么；不能通过记账自我授予权限。

## 3. 交付变更：用户可以改向，Agent 必须管理后果

**触发**：新输入会改变本轮范围、关键约束、共享基线、优先级、完成条件或在途工作安排。

### 3.1 影响与建议

先描述影响，不以“当前阶段禁止”代替判断。至少覆盖实质相关项：

- 哪项承诺增加、替换、延期或取消；与当前目标是否一致。
- 受影响契约、实现、数据、消费者和并行工作。
- 已完成成果哪些保留，哪些需调整；哪些验证仍有效，哪些待重验。
- 对依赖、关键路径、交付条件和风险的影响；不无依据报精确工期。

给一个推荐处置及原因：本轮吸收、用其他范围替换、下一轮、先探索、暂停或关闭旧交付。存在重要取舍且未有明确选择时，提出最小问题。可以合并相关变化说明，不能以统一表单为由反复打断。

用户明确坚持本轮加入或改变方向时，按该选择重排，不继续争取同一批准。新出现的安全、数据、费用等独立授权边界仍需处理。

### 3.2 更新与传播

1. 保存原承诺及改变原因，修订当前交付范围与完成条件；原目标取消不能被写成已完成。
2. 对相关需求、AC、接口、决定形成新的有效基线；必要时先保留候选，不能让同一适用范围有互相矛盾的现行规则。
3. 通知受影响工作者新的基线和处置：继续、重做局部、等待、暂停或取消；不要无差别暂停整个项目。
4. 标明证据需要复核的范围。不是全量清零，也不是因为“之前通过”永久有效。
5. 更新活跃工作、依赖、风险和下一步；对暂停工作保存恢复点。
6. 在有意义的变更点保存版本锚点；过渡状态显式标记，不在同步未完成时宣称新基线已全体就绪。

小变更可以在当前任务中闭环；重大或跨工作流变化保留独立可引用的变更条目，不强制独立文件。适用既有授权时不额外等“变更表批准”。

多次插单要评估净范围，而不只逐条评估。若原承诺被挤出、在制工作过多或验收对象不稳定，主动报告并建议收敛。用户可以选择继续扩范围，记录必须反映不再沿用原交付条件。

**结束条件**：影响有处置、相关责任与基线已同步，或未完成同步已由明确工作跟踪；不存在无记录遗弃的旧工作。

## 4. 进入审查与风险审批

实质变更按[多 Agent 审核与风险协议](<review-and-risk.md>)执行作者自证、两个互补独立发现视角、发现独立核验、去重处置、增量复审和风险分类/升级检查。微小确定性改动按该协议裁剪，不将“按风险”解释为默认不审。

评审结论不自动产生执行许可；风险路由不改变本文件第2节的授权语义。low可自主集成的前提是已有项目授权和适用检查通过；medium/high的人类决定可以复用实际覆盖该风险与候选的明确条件许可，但不能用旧代码绿灯替新提交背书。项目保留的人类审批与平台限制不可被Agent填名额或自写批准取代。

需要人时汇报经核验的少量重大决定，不转发所有原始意见；nit默认不执行也不自动转backlog。重大既有风险有处置，普通无关历史债不扩本轮。默认第三轮未闭环转策略，不第四轮继续常规互审，也不因上限自动通过。

范围、关键取舍或硬要求若需改变，回到本文件第3节；风险接受不把FAIL改PASS，不允许承担未授权的第三方后果。
