# 文档协作协议

本协议定义项目知识分层与共同编辑；语义变更按[决策与变更](<decisions-and-change.md>)处置，字段见[记录约定](<records.md>)。

## 1. 文档是协作接口，不是聊天与代码的转储

**触发**：创建、修改、导入、整合或审查项目资料。

先确定读者、用途、适用范围与信息归属，再决定写入位置和粒度。需要持久化不代表必须进入规格；某条信息与本次任务有关也不代表属于当前文件。模板帮助定位信息，不要求为不适用内容填空或机械拆文件。

## 2. 信息层次和越界判定

| 信息层 | 应表达 | 不应混入 |
|---|---|---|
| 目标与交付范围 | 为谁解决什么、成功条件、非目标、约束、承诺 | 局部函数执行过程、调试猜测 |
| 需求与验收 | 业务规则、条件、可观察行为、完成标准 | 私有变量、helper 调用、当前代码流水账 |
| 架构与接口 | 模块责任、依赖、共享数据与协议、公开标识、重要取舍 | 无长期约束价值的局部实现清单 |
| 工作与实现资料 | 任务、必要实现策略、定位线索、进度与交接 | 将临时工作路径提升为永久产品义务 |
| 决策、证据与历史 | 原因、观察、环境/对象、结果、偏差与处置 | 把推测写成已验证事实或隐式新增要求 |

判断公开标识是否必要：它是否被消费者依赖、被兼容性承诺约束，或确实参与验收？API 字段、配置键、CLI 参数、共享协议和特定架构限制应精确；内部变量或 helper 名通常不入规格。必要源码定位可以链接到实现，不复制整段代码解释。变动频繁的内部结构如果必须记录，应位于明确的实现资料并说明适用修订。

例如：

- 越界：“设置 `retry_count`，进入 `_run_retry_v2()`，写 `pending_map`，最后从对象中拿 `last_error`。”
- 需求：“临时网络错误发生后，客户端最多重试三次。达到上限后，客户端向调用方报告失败。已确认完成的操作不得被再次提交。”
- 实现资料：“重试实现与测试入口见源码链接。”

这里的三次是示例，不是 devloop 默认要求。真正需求还应按项目说明哪些故障可重试及副作用边界，不能只通过改句式掩盖语义缺口。

## 3. 受控工程表达

本协议借鉴 ASD-STE100 的受控表达思想，不照搬英语词表、不宣称符合该标准，也不规定统一句长。

### 3.1 区分语句效力

- **要求**：规范义务，应明确适用对象/条件与可观察结果。
- **决定**：已采纳选择，附必要范围、理由及来源。
- **事实**：已观察/验证的内容，不能把某次环境结果泛化为永久保证。
- **假设**：尚待验证的前提，影响重要结论时有验证责任。
- **提议**：尚未采纳的选项，不能混入现行正文充当要求。

不要求每句话加标签；用章节、状态或简短表述区分即可。观察到现有代码行为，不自动等于用户要求；某 Agent 建议也不等于已经采纳。

### 3.2 规范语句

- 明确主体、条件与结果；避免“它”“相关逻辑”“正常处理”却没有可识别对象。
- 一条要求尽量表达一个主要义务。可分开验证的义务不要用长串“并且”混在一起。
- “必须/不得”表达硬约束，“应当”表达有理由可偏离的推荐，“可以”表达许可或选择；不要把审查者偏好写成必须。
- 核心业务概念使用稳定术语；允许明示别名，不要求把所有私有代码符号收入词典。
- 避免没有标准的“合理、完善、高性能、充分”等结论；能量化则量化，否则说明判定依据与适用情境。
- 未知、未决定、尚未验证和不适用分别表述；不能用空表或“无特殊要求”掩盖尚未了解的风险。
- 标题和摘要支持查找，不用全量复述正文；跨层信息用权威链接，不平行复制。

## 4. 编辑：当前正文完整，历史另有锚点

### 4.1 编辑前

1. 阅读目标文件及相关现行规则，确认责任范围与基线。
2. 判断是纯整理、现状记录、候选提议还是语义变更。语义变更先取得适用决定，或明确保持候选，不静默生效。
3. 查明消费者、相关文档与证据；大改先明确整合边界，小改不必生成额外编辑计划。

### 4.2 编辑中

- 将有效内容整合到合适章节，替换已失效表述，维持读者从当前正文即可理解的连贯状态。
- 不在末尾不断追加“补充/最新修正”来解决同一范围的冲突。
- 当前规范可以重组、合并、删除被替代文字；保留重要承诺、决定与变化原因的 Git/记录锚点。
- 当前要求与未来候选共存时，明确适用交付、状态与基线，不能留给实现者自行猜测哪个优先。
- 代码注释、实现资料和工作报告各守职责；转移有用内容，不因“越界”丢掉必要证据。

### 4.3 编辑后

核对术语、重复、矛盾、引用与消费者；说明实质变化和证据影响。纯格式整理不应无故引起业务基线变动，也不能趁整理改变约束。

文档与实现的版本应形成可追溯整体。可在一个原子变更中共同提交规格、实现和测试，也可按项目需要分开提交；不得让中间不一致被误当可交付基线。无需强制“所有文档与代码永远拆 commit”。

**结束条件**：现行正文可直接理解，候选与事实有边界；受影响的引用、工作与验证已处置或明确跟踪。

## 5. 共享文档的协作

**触发**：多人/Agent 对同一规范或相关共享定义并行编辑。

1. 声明依赖基线、编辑范围和本次整合责任；同一人可兼多职，不设永久“唯一能改文档”的身份。
2. 默认由当前整合责任方收拢共享规范；规模需要时可按明确章节认领。通过独立增量提交提议，避免多个执行者同时覆盖权威工作副本。
3. 共享接口或规则改变时，通知实际消费者并说明何时生效；受影响工作先对齐，不让无关工作全部停摆。
4. 合并前对照最新基线，处理语义覆盖、术语、重复定义、适用范围和证据影响。Git 无冲突不是语义一致的证明。
5. 发生分歧，保留双方增量与争点，按[决策与评审协议](<decisions-and-change.md>)处理；不能“最后写入者胜出”。

**持久化**：在工作记录说明整合责任、依赖与生效基线，重要冲突处置进入已有变更记录。

**结束条件**：被采纳的现行规则一致，提议有处置，消费者获得可识别的基线；原作者不需要持续在线解释。

## 6. 记录的历史属性

| 类型 | 编辑方式 |
|---|---|
| 现行 Spec、AC、Interface、项目目的与当前计划 | 经适当决定受控修订；保留版本与重大变化原因，不只追加 |
| ADR 和重要决定 | 保留当时理由与结论；澄清可标注，实质替代建立新决定及替代关系 |
| 进行中的工作报告 | 随执行更新；区分计划、已完成、已验证与未验证，保留重要检查点 |
| 已结束执行、验收与发布结果 | 不静默改写发生过的结果；错误以可识别纠正说明更正，后续验证另记对象和时间 |
| 日志、原始证据 | 保留来源与身份；清理按敏感性/保留策略，不将日志全塞入规范 |

重要证据和决定保存必要摘要与稳定引用。不要复制密码、令牌、个人数据或生产数据到项目文档；使用脱敏样本和受控存储。敏感信息清理可以覆盖“保留历史”的一般要求，但要按实际政策处理已进入版本历史的泄露，不声称只删当前文字就解决。
