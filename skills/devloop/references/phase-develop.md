# DEVELOP：实现与持续集成

DEVELOP 把本次交付的承诺变成已集成、可验证的结果。按工作单元组织执行，不把模块数量、分支数量或代码合并等同于交付进度。

## 前提

- 本次工作依赖的要求、接口和重要决定可识别；未决项已隔离或明确阻塞。
- 相关工程能力满足当前需要，证据仍适用；缺口交给 [TEST_INFRA](<phase-test-infra.md>)增量处理。
- 按[工作协议](<work-and-delivery.md>)认领责任、依赖、工作区与整合范围；记录形式见[记录约定](<records.md>)。

## 动作

### 1. 拆分与协作

第一次写入前按[工作边界与版本控制选择](<work-and-delivery.md#11-动手前选择工作边界与版本控制>)核对分支、基线、未提交归属和活动执行者，主动决定继续、建分支或独立工作区；合适分支不重复创建，不能把开了分支误当已经隔离他人改动。权限内自行选择，重要例外记理由。

按可交付切片、模块、风险验证或集成责任拆分工作，不强制一个 Spec 模块对应一个执行容器。每项工作明确完成条件、依赖基线、消费者和交接入口。

并行可写工作使用隔离工作区；共享接口、schema、路由、配置与规范明确整合责任。Mock 支持并行，但不消除真实接口和集成依赖。

### 2. 实现并尽早连接关键路径

- 尽早建立最小业务纵切片，验证构建产物、真实接口与核心消费路径，不等所有模块完成才第一次联调。
- 围绕承诺、重要边界与风险选择实现和测试方法；可使用 TDD，但不以固定测试编写顺序代替结果依据。
- 重要安全、性能或依赖未知及时验证，不因为所属测试层通常在后续阶段就延后反馈。
- 可复现缺陷默认先捕获最小失败用例，再修复并验证原故障与受影响行为，保留缺陷/工作来源；紧急保全或不能可靠复现时说明顺序例外、限制与替代证据，不伪造红绿结果。
- 实现细节和调试线索归工作或实现资料；现行规范的编辑与共享整合遵循[文档协议](<documentation.md>)。

### 3. 在最新相关基线上集成

提交、集成或声明完成前自检实际 diff：范围、意外文件/秘密、契约与断言变化，确认没有夹带或削弱标准；再选择适用构建、类型/lint与测试入口，不用早先绿灯代替最终检查。按实际依赖顺序整合工作，合并前核对最新相关契约与集成基线。在拟合并结果上验证受影响行为，不能拼接不同分支的 PASS 证明不存在的组合通过。

处理语义冲突和共享汇聚点，记录集成位置、结果及待办。工作已实现但等待集成，应如实保留状态；不能先声明本轮承诺全部完成。

### 4. 保持进度与证据

按[工作与证据协议](<work-and-delivery.md>)在重要变化、阻塞、集成和停止时更新记录。区分已完成、已验证与待验证，保存环境/对象和必要证据引用。

审查 PASS 是否对应实际行为和断言，失败或跳过是否有解释。禁止删断言、放宽标准或静默跳过来取得绿灯；质量指标与文件齐全不能替代实质验证。

## 退出依据

对提出验收的交付范围，确认：

- 承诺的实现已集成，相关接口、构建和配置与基线一致。
- 关键路径已连接，受影响验证有效，未完成或偏差有明确处置。
- 工作结果、责任、实际集成位置与证据可定位。
- 可形成明确候选对象及验证条件，交给 [SYSTEM_TEST](<phase-system-test.md>)验收。

这不是生产发布许可，也不要求无关的下一版本工作全部停止。仅局部工作完成时更新局部状态，不把所有 Plan 的结束数量当验收依据。

## 变化、失败与中断

- 用户插单或改向：按[变更协议](<decisions-and-change.md>)说明净范围和交付影响，采用明确选择并同步承诺、工作与证据，不直接丢下当前任务。
- 发现契约缺陷或关键方案不可行：对受影响范围开展 [DESIGN](<phase-design.md>)，通知消费者并保留无关成果。
- 发现工程能力或环境问题：修复对应缺口并重验相关结果，不让整个项目倒退。
- 评审争议按[评审协议](<decisions-and-change.md>)分级与收敛，偏好不自动阻塞，新实质风险不能忽略。
- 中断后先只读盘点并确认安全接管，再验证和继续；不得自动丢弃分支、未提交成果或重复启动在途任务。
