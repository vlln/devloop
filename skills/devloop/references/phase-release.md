# RELEASE：交付、接收与后续改进

RELEASE 将被接受的候选交给实际消费者，确认接收结果与后续责任。发布、部署、交付本地制品或内部成果均按真实消费方式处理，不以打 tag 代替交付。

## 前提

- 本次交付范围、验收结论和候选身份可定位，或适用已授权的紧急修复路径。
- 已明确消费者、目标环境、必要操作、支持边界及交付责任。
- 按[决策与授权协议](<decisions-and-change.md>)核对现有许可、条件与限制；有效的条件授权可复用，技术评审通过不自动产生发布权限。
- 交付记录与证据入口按[记录约定](<records.md>)组织，操作及恢复遵循[工作与交付协议](<work-and-delivery.md>)。

## 动作

### 1. 核对候选和交付就绪

确认实际交付对象与已接受对象一致。重新构建、配置、手工冲突解决或依赖变化时，按[审核与风险协议](<review-and-risk.md>)判断差额复审/再判级及许可覆盖，不能因版本号相同或旧批准就假设仍被覆盖。既有方向决定可以保留，候选质量结论只覆盖实际审过的对象。

根据公开兼容性与消费者影响主动选择版本号和交付方式，沿用项目策略；包/API 可采用 SemVer，不按 commit 类型机械推导，也不因版本已选就视为获准打 tag 或发布。准备消费者需要的安装/使用说明、兼容变化与已知限制。服务型交付按风险准备环境、观察指标、阈值、窗口和停止条件；无持续服务不强制制造生产监控。

### 2. 准备可行且有授权的恢复

对数据迁移和外部副作用明确可逆性、兼容窗口、备份/恢复验证与失败处置。策略可为停止、回滚、前向修复或升级；不可逆迁移不无条件回滚旧二进制。

确认恢复动作也在许可范围内。事先约定的触发条件成立时可执行获准策略，不重复询问同一决定；没有覆盖的高后果动作须澄清，不能以紧急或回滚为名扩大权限。

### 3. 执行并核验实际接收

- 使用项目适用的发布、部署或交付路径，保留候选、目标、关键操作及结果锚点。
- 在消费者实际安装/运行环境核验核心路径与约定观察条件，记录实测和限制。
- 核对合并、版本标签、制品位置和变更说明是否与事实一致；标签存在不证明发布成功。
- 分开记录已交付、验收接受和运行验证；交付动作失败不能写成版本已完成。

### 4. 交接与关闭

明确后续告警、支持、事故响应及环境接收责任；凭证和敏感资料使用受控渠道，不复制进普通文档。按需说明兼容/弃用、支持终止与退役安排。

记录本轮范围处置、交付结果与未决问题，更新版本变更摘要。复盘聚焦影响下一轮做法的经验，问题进入有责任的修复或候选工作，而不是例行堆长文。

## 退出依据

- 已接受的对象或经评估覆盖的变体已交给目标消费者，实际接收结果有依据。
- 适用观察与核心路径核验完成；限制、失败或风险处置如实保留。
- 后续支持、恢复、未决事项与历史记录可定位且有归属。
- 本次交付明确关闭、待补充、取消或转入支持，不用一个状态掩盖不同结果。

后续候选经采纳形成新的交付承诺，再开展 [DESIGN](<phase-design.md>)及所需工程工作；不自动实施全部 backlog，也不强制项目永远开始下一轮。项目结束或转向时保留成果与支持/归档责任。

## 失败、热修复与变化

- 交付前发现业务或契约问题：交 [DEVELOP](<phase-develop.md>)或 [DESIGN](<phase-design.md>)局部修订，必要时由 [SYSTEM_TEST](<phase-system-test.md>)重验候选。
- 部署、环境或流水线问题：修复当期能力并评估影响；不能把环境故障直接当作业务验收通过或失败的完整依据。
- 运行不健康：按事先策略保全与恢复，记录实测、动作及结果；无法安全处理时停止扩大影响并升级。
- 紧急事故按已有授权先恢复关键能力，保留必要回归和交付证据，随后补足记录；不夹带无关功能或无限豁免验收。
- 用户改变发布范围、目标或时机：按[变更协议](<decisions-and-change.md>)更新承诺、候选与许可覆盖，保留已发生外部影响，不伪称可撤销。
