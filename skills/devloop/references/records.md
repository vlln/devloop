# 项目记录约定

本文件是默认记录字段、状态与权威归属的唯一约定。项目已有任务平台、文档和分支策略时可映射使用；在入口说明映射，不强制复制第二套记录。

## 1. 默认归属与路径

| 信息 | 默认载体（目标项目根目录下） | 职责 |
|---|---|---|
| 入口与常驻行为 | AGENTS.md、docs/devloop.md | 项目边界、新输入、文档协作与恢复的最小义务 |
| 当前导航 | docs/README.md | 活跃交付、工作和待决事项的权威链接；不单一全局阶段 |
| 项目目的 | docs/vision.md | 用户、成功条件、非目标和重要约束 |
| 交付承诺 | docs/deliveries/000x-name.md | 范围、基线、阶段关口、里程碑、风险、变更与接收条件 |
| 需求与验收 | docs/spec/、docs/ac/ | 可观察行为及完成标准，稳定 ID |
| 共享接口 | docs/interface/ 或可生成契约 | 公开字段、协议、兼容约束；避免手写与机器契约双源 |
| 重要技术决定 | docs/adr/ | 取舍与约束；不是全部内部实现说明 |
| 工作单元 | docs/plans/000x-name/ | README 索引，Plan 与 Report 成对；可包含多个子任务 |
| 候选与以后工作 | docs/backlog.md | 待澄清/候选与已排期分开，不把全部问答变任务 |
| 工程约定与用户变更史 | CONTRIBUTING.md、CHANGELOG.md | 项目实际命令/策略与已交付变化；不是内部执行日志 |

决定、授权、评审、验收与发布记录可放入相关交付或 Report 的可定位章节；重大跨范围事项才按需独立。一个信息只维护一个权威记录，其他地方用链接。

新项目默认采用上述路径；内容不足以独立成文时可合并并在入口映射。模板仅是骨架，安装不要求保留全部空目录和示例。参考模板后移除实例中的说明性占位，模板不算真实成果；删除或替换模板时同步索引。

## 2. 标识、基线与命名

- 默认编号 `0001` 起递增，类型内唯一；backlog 条目可用 `BL-0001`，需求/验收使用项目约定的稳定 ID。现有 ID 不为升级改名。
- 并行工作由当前协调责任方分配编号与认领；发现冲突先保留增量再整合，不后写覆盖。
- 同一逻辑条目的 ID 不复用于不同义务；替代、拆分与移除保留关系或历史锚点。
- 基线由可识别修订（如 Git 提交）、文档/条目 ID 和适用交付共同确定；Spec 可保留原有整数 version，不要求每个文件都造版本表。
- 多个 Spec/AC/接口可以同时 active；同一适用对象与范围不能有矛盾现行要求。下一交付的候选须明确标出，不暗中覆盖当前交付。
- 分支、工作树、PR 与工作单元可映射；沿用原生策略；无策略时默认主干＋短期工作分支，只有发布维护需求支持时再采用 develop/release 或 Gitflow。文档/代码/测试可原子共同提交，或按项目规范分开，需保持可追溯的一致候选。

## 3. 元数据与状态

正式 Vision、Spec、AC、Interface、ADR、Delivery、Plan、Report 使用 frontmatter：`title`、`description`、`type`、`status`。`description` 用于判断相关性，不复制正文。模板默认 draft/pending/planned，不预先声称内容已接受。

`created` 仅在真实已知时填 ISO 8601 时间；不填伪日期。Spec 的 `version` 可延用整数。交付/Plan 的结束结果使用 `outcome`（或正文同义明确结果）；适用交付、基线、负责人等可放正文，不重复维护两份。

| type | 默认 status | 意义 |
|---|---|---|
| vision/spec/ac/interface | draft → proposed → active | 编写、待采纳、现行；采用取决于有效决定与必要评审，不是额外审批仪式 |
| adr | draft/proposed/accepted/superseded/deprecated | 保留决定与替代关系，重要变化建立新决定 |
| delivery | planned/active/paused/closed | planned 是承诺已形成未开始，active 执行，paused 有恢复条件，closed 有结论 |
| plan | pending/active/blocked/paused/done | 未开始、进行中、有阻塞、暂停、执行结束；不把 done 当成功验收 |
| report | draft/complete | 记录进行中或已经完整；complete 不等于工作成功 |

Delivery 关闭时 `outcome` 为 `delivered`、`cancelled` 或 `superseded`；未交付而放弃按 cancelled 并说明失败原因。Plan done 时 `outcome` 为 `succeeded`、`failed`、`cancelled` 或 `superseded`。被取消目标不算完成交付。

Backlog 默认 `candidate`（可待澄清）、`open`（已定性未承诺）、`planned`、`done`、`dropped`；done 要说明实际闭环对象，不统一假定已上生产。

AGENTS、常驻规则、CONTRIBUTING、CHANGELOG、backlog、README 不要求 frontmatter。既有项目可保留不同状态词，但需有清楚映射并分离执行状态与结果，不能自动把旧 done 转为 succeeded。

## 4. 最小信息，不是强制每项新文件

### 交付记录

目标/接收者，范围/非目标，需求与证据基线，里程碑和关口状态，验收及交付条件，关联工作/责任，风险/假设/外部依赖，重要决定/授权与变更，验收和接收结论，遗留/支持与下一轮处置。

阶段尚未满足时写缺口和责任；关闭交付才需要接收结论，不能提前填 PASS。一个版本 design、另一个验收时分别记录，不覆盖单一全局 phase。

### 工作记录

所属交付、目标/完成条件、当前责任、依赖基线、工作区/分支及整合责任、边界、当前状态、结果/证据和下一步。计划重大修订保存原承诺与变化原因；报告区分已完成、已验证、未验证、剩余、运行任务和接管提示。

### 决定与授权

内容、来源定位或忠实摘要、对象/环境/范围、限制与条件、关联基线、替代/撤回。记录不产生原本没有的许可；不能编造签名或消息编号。复用与差额询问见[决策协议](<decisions-and-change.md>)。

### 证据与完成声明

可定位要求/风险、候选/构建、方法、环境/关键配置与数据、结果与限制、产物位置。验收接受者与决定依据、交付目标和运行观察分开记录。存在变更时注明哪些复用、哪些待重验；不能把失败改成 PASS 来表示接受风险。

### 风险与候选

重要风险有依据、责任、触发/复查条件、验证/缓解及残余处置；候选有来源和处置，不自动成为当前范围。

## 5. 更新与保存

按[工作协议](<work-and-delivery.md>)在决定、范围/阻塞变化、集成、交接和停止时保存。当前规范按[文档协议](<documentation.md>)整理；已发生结果纠错要可识别，不能静默改写历史。项目入口维护导航与汇总责任，具体工作者维护自己的事实，避免共享入口互相覆盖。
