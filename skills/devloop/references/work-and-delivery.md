# 工作、进度与交付协议

本协议定义工作认领、进度、风险、集成、恢复与交付；授权和范围变化见[决策协议](<decisions-and-change.md>)，记录字段见[记录约定](<records.md>)。

## 1. 工作认领与合作

**触发**：拆分、委派、接管或开始一项需跟踪的工作。

工作可以是模块、跨层切片、风险探索、工程准备、集成或交付。采用项目已有任务系统或 Plan/Report；微小工作可作为既有单元的一步，不为每个命令创建容器。

开始前能回答：

- 归属哪个项目/交付，目标与完成条件是什么？
- 谁当前负责，依赖哪些基线和先行工作？
- 工作区/分支在哪里，可编辑什么共享范围，谁负责整合？
- 有哪些不能越过的授权、数据或环境边界？
- 完成或中断后从哪里接手，结果由谁消费？

责任可由人、Agent 或单人兼任，不要求创建完整角色组织图。委派前在权威工作记录认领，避免两个执行者无意重复；没有共享写入能力时由协调方串行分配 ID 与认领。发现并发认领冲突先保留各方成果，再确定责任与整合方案。

并行可写工作使用独立 worktree/等价工作区；共享文档按整合责任处理。分支与工作单元应可映射，但不把“一容器只能一分支”强加给跨仓库协作。依赖是实际接口与就绪条件，不因前后端使用 Mock 就宣布无集成依赖。

**结束条件**：活跃工作有明确责任、边界与入口，相关依赖可识别；不是仅在聊天里分派。

## 1.1 动手前选择工作边界与版本控制

**触发**：准备开始可写工作、切换到另一项任务，或范围/协作方式实质改变。不是每次编辑都重新选择，也不是等用户提醒才考虑。

先只读核对项目策略、当前分支与基线、未提交改动归属、其他活动执行者，以及将触及的文件和共享资源，再选择：

| 情境 | 默认动作 | 边界/例外 |
|---|---|---|
| 已在属于本任务的合适工作分支 | 继续并记录位置 | 不为每个步骤再套一层分支 |
| 在共享主干上开始独立功能、重构或有风险修复 | 写入前建立短期工作分支，默认从相关最新集成基线开始 | 项目明确采用主干开发或用户指定分支时沿用，但仍检查隔离和恢复依据 |
| 另一项工作尚未结束，或准备并行可写 | 独立分支配合 worktree/等价工作区 | 分支本身不隔离文件、端口、数据库和构建目录；先界定共享资源 |
| 小型、低风险文档修正，且项目允许直接提交 | 可沿用当前分支 | 文档变更若改变共享契约或范围，不因文件类型就视为低风险 |
| 新项目首次建档 | 可直接初始化主干，建立初始锚点 | 随后开始独立实现前再次选择；无策略时默认主干＋短期工作分支，不先引入 develop/release 长期分支 |
| 有未知、他人或无关未提交改动 | 保留并识别归属，必要时另用安全工作区 | 不擅自 stash、reset、搬动、提交或清理；不能假设新建分支就消除了已有改动 |

分支/工作区/检查点的选择在现有权限内自行完成，不逐项向用户申请。影响重要取舍、存在权限缺口或无法安全保留他人成果时才提问。没有 Git 的目录先确认项目是否需要版本历史；devloop 软件项目默认使用本地 Git，不擅自建远端或上传。平台限制和用户对提交等操作的边界仍适用。

首次选择形成项目工程约定；日常按约定，事实变化时重评。项目级主干、命名、合并与版本策略写工程约定；本任务的基线、工作位置及重要例外写工作记录。简单选择不需要新 ADR 或单独表单。

## 1.2 关键节点的工程选择

这些是主动判断点，不是待用户点名的可选服务，也不是每次都展示给用户的清单。优先沿用有效项目约定；未覆盖时采用默认，重要偏离说明理由并就近记录。

| 触发节点 | 应主动判断并采用的默认 | 裁剪与重新评估条件 |
|---|---|---|
| 工作范围增长或准备并行 | 优先拆成可独立验证的小切片；仅在边界、依赖和整合责任清楚且收益大于成本时并行 | 紧耦合且协调更贵时串行；不可为凑并行人数硬拆 |
| 关键依赖/技术方案有可能推翻实现的未知 | 先做最小可复现实验，再投入完整实现；保存条件和结论 | 已有适用证据可复用，不为熟悉依赖重复做形式验证 |
| 改公开接口、数据结构或持久化格式 | 先选兼容/迁移与验证方案，默认避免无意破坏现有消费者；必要时分阶段切换 | 经明确范围决定的破坏性变更可做，但需告知迁移、版本与恢复影响 |
| 新增/修改行为 | 从可观察要求设计验证，主动考虑正常、边界和失败风险；优先增量实现并及时运行相关检查 | 不强制每条 AC 四格或统一 TDD；低风险改动选择最小充分证据 |
| 修复可复现缺陷 | 默认先捕获最小失败复现/回归用例，再修复并验证原故障和受影响行为 | 紧急保全或不可自动重现可调整顺序/证据，但说明限制；不伪造红绿 |
| 准备重复多人/多轮开发 | 将确定、反复发生的重要约束接入现有测试/lint/CI；关键新门禁做受控失败自证 | 不因“所有项目”叠加复杂度、覆盖率或架构工具，阈值要对应真实风险 |
| 准备提交、集成或声明完成 | 自检实际 diff、范围、意外文件/秘密、契约及测试变更，选择受影响检查并在集成候选验证 | 提交不等于允许 push/发布；不能用已跑检查替代最终 diff 核对 |
| 长任务、切换方向或停止 | 在有意义的完成点保存可恢复增量与下一步；按项目权限选择 checkpoint/commit | 不能为留锚点提交用户无关改动；不机械每步 commit |
| 形成发布候选 | 根据公开兼容性和消费者影响选择版本、变更说明及发布方式，并确认冒烟/观察/恢复 | 采用项目既有版本策略，SemVer 适合包/API时可作默认；不以提交类型机械决定版本或默认获准打 tag |

具体执行与退出证据仍遵循下文；这些默认不降低授权、独立评审和交付门禁。

## 2. 进度与计划修订

### 2.1 最小状态表达

默认工作状态：待开始、进行中、阻塞、暂停、已结束。已结束另记结果：成功、失败、取消或被替代。既有项目可映射原生状态；不得让同一个 done 同时暗指成功验收与执行失败。

每项活跃工作维护当前负责人、依赖/阻塞、实际进度、下一步和最近证据。交付记录维护承诺范围、里程碑、接受/交付条件、已集成与待完成工作。项目入口引用这些记录并提供活跃交付总览，不重复维护全部任务字段。

计划可以修订；保留原承诺和修订原因、当前范围与决定来源。重大范围变化遵循变更协议。实施完成但验收未完成应明确表示，不因代码合并就算业务承诺全部兑现。

### 2.2 更新时机

在重要决定、范围变化、里程碑、阻塞/解除、工作认领/交接、集成与计划性停止时更新。长任务在可恢复的检查点保存，不要求逐工具调用写报告。对可能中断的高成本任务，先保存任务 ID、工作位置与获取状态的方法。

项目汇总由当前协调责任方整合；各工作者更新自己的事实并提交变化，不同时随意重写全局入口。可使用任务平台记录及链接；不能让只有临时工具 todo、聊天或不可访问的后台任务成为长期唯一状态。

**结束条件**：新的接手者能知道本轮还承诺什么、谁在做什么、哪些受阻以及下一步，而不是只知道阶段名。

## 3. 风险、假设和外部依赖

**触发**：可能影响交付的重要不确定性、外部承诺或失效条件。

在现有交付/决策/工作记录维护：风险或假设、依据、责任、触发或复查条件、验证/缓解措施、影响交付和残余处置。不要给每个想象中的问题建登记项；聚焦会影响决定与交付的事项。

高风险的安全、数据、性能和依赖兼容问题尽早定向验证，不机械等待系统测试。外部团队、第三方 API、付费资源等依赖要明确可用性与限制；未知当未知，不用 Mock 绿灯证明真实依赖已经可用。

风险被接受需有实际承受后果的一方及适用授权。接受风险不等于可以将未满足的硬要求算通过；必要时修订范围/条件或阻塞。定期复查可由里程碑与事实变化触发，无需固定会议仪式。

**结束条件**：重要风险有处置或明确阻塞，假设不被遗忘为既成事实，依赖等待有下一步。

## 4. 集成与基线更新

**触发**：共享变更准备集成、契约修订、依赖就绪或交付候选形成。

- 尽早用业务最小纵切片连接真实关键路径；Mock 用于隔离与高频验证，不代替最终依赖验证。对有费用/配额/破坏性副作用的外部调用，使用有边界的隔离验证，不放任高频流水线消耗。
- 依赖顺序决定集成顺序；独立工作先就绪先整合。共享 schema、路由、配置、公共规范等明确整合责任。
- 合并前核对最新相关基线，处理语义和文本冲突；在拟合并结果上验证重要影响，而不是只引用旧分支绿灯。
- 工作完成后记录集成位置及证据；等待集成不是已交付。跨仓库依赖显式标明组合版本与兼容窗口。
- 失败按实现、契约、工程能力或环境问题定位，分配相应工作。失败原因服务于修复，不必让整个项目阶段来回切换。

**结束条件**：结果已在目标基线整合或等待事项明确；无未通知的共享契约变化；相关检查有效。

## 5. 停止、交接与恢复

### 5.1 计划性停止

保存工作位置、最近版本与未提交改动状态、已完成/已验证/待验证内容、重要后台任务及 ID、阻塞、下一步和适用决定链接。必要时按项目策略创建 WIP 锚点，不能为保存状态擅自提交用户无关内容或泄露敏感信息。

暂停明确恢复条件；取消说明成果保留和依赖处置，不伪称已完成原目标。清理工作区需要先核对位置、未提交成果与其他执行者，再按权限操作。

### 5.2 恢复步骤

1. 读项目入口、当前交付与相关工作记录，确认目标、范围、基线和授权边界。
2. 只读盘点现实：当前目录/仓库、分支和 worktree、未提交改动、仍在运行的任务与产物；不重复启动已有任务。
3. 明确旧执行者是否仍活动；接管前协调责任，确认可以安全操作的工作区、验证与共享资源范围。无法确认时不改动该工作区，不启动可能抢占资源的验证；不凭文件时间老旧判定可以接管或清理。
4. 在已明确可安全操作的范围内，核对最后检查点与当前状态是否一致。重跑最小必要验证，或说明可复用依据；证据变化按第 6 节处理。
5. 记录差异及处置：继续、修复、重新验证、交接、暂停或废弃。保留有效成果，不因崩溃自动丢弃分支。
6. 更新当前责任和下一步后继续；无法恢复重要执行授权时仅暂停相关动作并澄清。

**结束条件**：接手者已核对实际状态及接管责任，当前工作可继续或明确等待；不是简单复读上次阶段。

## 6. 证据与验收

### 6.1 证据适用性

支撑重要声明的证据至少可定位：被验证要求/风险、对象与修订/构建标识、方法/命令、关键环境与数据条件、结果、限制及原始产物位置。可复用项目原有测试结果，不要求手写每条测试的重复报告。

需求、代码、依赖、配置、环境或数据条件改变时，判断哪些证据仍有效。待复核项标明关联变化与重验责任；不自动清空全部证据，也不因同一测试层已跑过而禁止回归。无法判断关键证据适用性时，该声明暂不成立。

聚合证据要确认对象一致；各分支的 PASS 不能拼成从未运行过的集成候选 PASS。格式完整、覆盖率数值和 AC 列表不能代替业务行为断言；禁止靠删断言、隐藏失败、无解释跳过来取得绿灯。

### 6.2 验收

**触发**：某次交付提出候选结果供接收。

1. 明确本次承诺、要求基线、候选对象和实际消费方式；包含适用的非功能要求与风险。
2. 核验实际拟交付结果：安装后的包、二进制、部署服务、生成的 Web 产物或其他消费者真正使用的交付物。开发环境绿灯不能替代。
3. 汇总有效证据、未满足项、已知缺陷、偏差与残余风险，说明接收建议。
4. 区分测试结论、技术评审与验收接受；接收责任方可按用户委托由 Agent 承担，不强制再走人类仪式。例外由适用有权者处置，不能静默降低标准。
5. 候选改变时评估验证与接受是否仍覆盖，重新验证/决定必要差额。

**结束条件**：明确接受、待补充或拒绝及其范围与依据。实施完成不等于验收通过；接受某项风险不等于测试结果从 FAIL 变 PASS。

## 7. 交付、运营接收与下一轮

**触发**：验收接受的对象准备交给消费者，或按已授权紧急路径交付修复。

1. 核对授权、候选身份、版本、环境与前提；交付内容必须与已接受对象相同，或有明确的变化影响判断和补充证据。
2. 准备消费者所需的安装/使用、兼容说明和支持边界；服务型交付按风险准备监控、数据迁移与恢复。
3. 执行有授权的交付，记录版本/产物、目标、必要操作、结果与可追溯锚点；打 tag 本身不证明消费者已收到。
4. 在实际消费/运行环境核验核心路径和预先约定观察条件。失败按适用策略停止、回滚、前向修复或升级，不现场任意扩大操作权限。
5. 完成接收与支持交接，记录已交付、运行验证及未决事项。后续事故、经验和需求回流，不自动启动所有候选工作。

恢复策略必须考虑数据可逆性与外部副作用；有不可逆迁移时，不无条件“默认回滚代码”。事先明确兼容窗口、备份/恢复验证、停止条件和实际获准动作。紧急情况下先按既有授权保全与恢复，事后补足记录，不能借紧急路径夹带无关功能。

按项目需要明确告警/支持责任、凭证与环境接收、弃用/兼容承诺、终止支持或退役条件。无持续服务的项目不强制监控仪表盘；有持续运营责任的项目不能因发布结束就无人负责。

交付关闭时，确认范围处置、问题归属与历史记录；复盘聚焦改变下一轮行为的经验，而非例行长文。下一轮从候选与实际反馈形成新的承诺。一个项目结束或转向时，也要明确保留成果、支持/归档责任及未完成目标，不能永远自动进入 DESIGN。

**结束条件**：交付结果和接收状态有依据，后续责任有归属；下轮候选与本轮关闭不混同。
