# devloop 常驻协作简规

本规则供项目内的人和 Agent 共同使用，不以加载外部 skill 为前提。项目工具可以映射下面的载体，但应在[项目入口](<../AGENTS.md>)说明权威归属。

## 生命周期与承诺

项目维护长期目标；[交付记录](<deliveries/README.md>)维护一次承诺、基线、条件和变化；[工作记录](<plans/README.md>)维护认领、依赖、结果与恢复点。立项、需求与架构、工程准备、实现与集成、验收、交付和反馈均要有依据；局部活动可以重叠，不以一个全局阶段阻止其他交付。开始某活动不等于已通过交付关口。

新输入先对照当前承诺。只问可行性不自动实施；重要插单应说明被增加/替换/延期的范围、依赖和证据影响并建议处置。用户明确改向后执行，并同步工作与完成条件，保留原承诺及有效成果。连续插单要看累计净范围，不能逐条接单而失去稳定交付对象。

## 工程选择：触发时主动做，不等用户点名

项目策略见[工程约定](<../CONTRIBUTING.md>)。首次选择形成约定，日常沿用，范围或协作事实改变时重评；权限内自行决定，重要例外简述理由，不逐项问批准，也不每次编辑展示清单。

| 时机 | 默认选择及边界 |
|---|---|
| 开始可写任务/切换任务 | 只读核对分支、基线、未提交归属与活动者；合适工作分支继续，共享主干上的独立功能/重构/风险修复先建短期工作分支；并行或另一工作未完则用独立工作区，另核对端口/数据等共享资源 |
| 新项目无策略 | 初次建档可在主干；后续默认主干＋短期工作分支，有实际发布维护需要再加 develop/release；明确主干开发策略可沿用，低风险修正按许可简化 |
| 未知或他人改动 | 先保留识别，不擅自 stash/reset/搬动/提交；新分支不自动隔离已有改动，必要时另选安全工作区 |
| 范围增长/准备并行 | 拆可独立验证切片，边界与整合清楚且收益足够才并行；紧耦合可以串行 |
| 关键未知/接口数据变化 | 前者先最小实验，已有适用证据可复用；后者先确定兼容/迁移、消费者和验证方案，避免无意破坏 |
| 行为改动/缺陷修复 | 从可观察要求选择正常、边界和失败风险验证；可复现缺陷默认先留失败用例再修复，不强制每条四格或统一TDD；紧急/不可重现时记限制和替代证据 |
| 重复开发/准备提交集成 | 反复重要约束优先接现有自动检查；自检实际 diff、意外文件/秘密、范围、契约和断言，在集成候选做受影响验证；不为凑工具加门禁 |
| 长任务/停止/发布 | 保存有意义检查点，不夹带无关改动；按公开兼容影响选择版本和说明，发布方式、冒烟、观察与恢复按风险确定，不因 commit 类型直接决定版本或获得发布许可 |

## 决定、授权与评审

- 区分需求确认、技术可接受性和执行授权。复用仍覆盖来源、对象、环境、限制与条件的已有授权，只询问差额；“方案不错”不自动允许上线、付费或删数据。
- 决定在就近权威记录保存内容、来源定位/忠实摘要、边界、条件及替代关系，其他位置引用。不得编造消息 ID、用户签名或缺失历史；记录本身不产生权限，项目记录不能绕过平台限制。
- 重要操作许可无法可靠恢复时只暂停相关动作并澄清。新信息或用户撤回影响哪部分，就重新判断哪部分。
- 评审针对对象、用途、约束和已接受取舍，按风险确定必要的独立视角。作者自称换角色不替代独立审查；无法取得时标明限制和关口缺口，选择等待、定向验证或有权者明确例外，不自行宣称满足。
- 阻塞需要要求/风险依据、位置、证据或故障路径、后果与关闭条件；偏好和未来扩展是非阻塞建议。
- 复审聚焦原问题和修订影响；新证据仍可重开重大风险。达到条件即收敛，超预算不自动放行。风险例外需有权者处置，不能把 FAIL 改写为 PASS。

## 文档表达与共同编辑

现行 Vision/Spec/AC/Interface 和计划经适当决定可整理修订，保持单一、连贯的当前规则，不把新规则无限追加到末尾。Git、决定和结果记录保留历史，已发生结论的纠错明确标记。

写作区分要求、决定、观察事实、假设与提议；要求明确主体、条件和可观察结果，尽量一条主要义务。核心术语稳定；高层规格不写私有变量、helper 调用和调试流水。公开 API 字段、配置键、CLI 参数及兼容约束是精确契约，不应因“禁实现细节”而删去。未知、未决定、未验证和不适用分别说明。

并行工作先明确依赖基线、可编辑范围和整合责任，使用独立 worktree/等价工作区。共享规范由明确的当前责任方整合；核对最新基线、语义冲突、重复和失效引用，不能“最后写入者胜出”。基线改变要通知受影响消费者，并处置其工作、测试和证据；无关工作不清零。

## 进度与恢复

重要决定、范围变化、阻塞、集成、交接与计划性停止更新记录。长任务保存有意义检查点及后台任务 ID/状态获取方法；不以临时 todo 或聊天作为唯一长期状态。

接手按顺序：读承诺和工作记录 → 只读盘点分支/工作树/未提交成果/任务 → 确认原执行者、接管责任与安全资源边界 → 再做可能有副作用的最小验证 → 更新差异、责任与下一步。无法确认时不抢占或清理工作区，不重复启动昂贵任务；不因中断丢弃成果。

## 验证、验收和交付

开发中尽早连接关键业务纵切片，测试按实际影响选择与重跑，不按阶段禁止某层验证。证据绑定需求/风险、候选对象、方法、环境/数据、结果与限制；代码、契约或环境改变时只使受影响证据待复核。Mock 不证明真实依赖可用，付费/破坏性外部调用须隔离且有授权。

验收核验实际拟交付的包、服务、Web 产物或其他消费对象，不只源码树。实现完成、测试通过、技术可接受、验收接受、实际交付和运行健康分别留结论。交付候选需与已接受对象相同或有变化评估及补充证据。

按风险准备安装使用、兼容、监控、支持与恢复；不可逆数据迁移不套用无条件代码回滚。交付关闭记录范围处置、剩余责任与改进回流；候选改进不自动成为下一轮承诺。

## 记录状态与模板实例化

正式类型文档使用 frontmatter：`title`、`description`、`type`、`status`。`created` 仅在真实时间可知时写入，不填虚构时间；Spec 可保留整数 `version`。索引、简规、backlog、CHANGELOG 不需 frontmatter。

| 类型 | 状态与结果 |
|---|---|
| vision / spec / ac / interface | `draft` / `proposed` / `active`；多个文档可 active，但适用对象不得冲突 |
| adr | `draft` / `proposed` / `accepted` / `superseded` / `deprecated` |
| delivery | `planned` / `active` / `paused` / `closed`；closed 必须注明 `outcome: delivered/cancelled/superseded` |
| plan | `pending` / `active` / `blocked` / `paused` / `done`；done 必须注明 `outcome: succeeded/failed/cancelled/superseded` |
| report | `draft` / `complete`；complete 只表示记录完整，不表示工作成功 |

模板是填写参考，不是已承诺、已执行或已批准的记录。复制后填写真实内容，去掉说明性注释，按实际阶段设状态；未知项明确跟踪。首个正式文档建立后可清理对应模板，但必须在同一次变更中更新索引与引用，避免死链。已有项目可映射原生载体和状态，保留 ID 与有效历史；导入现状不伪造需求或选型理由。
