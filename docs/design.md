# 设计目标

devloop 是安装到项目中的专业软件开发生命周期规范。它组织从立项、需求与架构、工程准备、实现与集成，到验收、交付、运营反馈和多轮改进的连续工作，使人和 Agent 能有文档、有历史、可并行、可合作地推进长期项目。

本次重设计依据用户确认的专业 SDLC 方向与后续审计/候选草案。目标不是仅缩减旧技能，也不是替换成三本记忆账，而是补齐真实项目变化下的共同事实、共同承诺与交付连续性。

开发背景保存在[重设计记录](<redesign/README.md>)；运行权威入口是[SKILL](<../skills/devloop/SKILL.md>)。本文件解释 why，不复制状态枚举、模板字段或完整操作协议。

## 1. 持久价值与控制边界

模型越强，越不需要解释通用工程方法，但仍受会话中断、协作者独立、上下文不完整和外部授权边界约束。专业项目规范的价值因此在于：

- 外部化有效目标、决定、进度和证据，使接手无需完整聊天历史。
- 为独立工作者建立共享边界、影响传播和集成责任。
- 让工程声明可以追溯，防止范围漂移、虚假完成与未授权副作用。
- 保留从目标形成、实施、验收到实际接收和反馈的生命周期，而不是只留文件格式。

规范规定必要责任、退出依据和脆弱协作点；工程方法按项目选择。模型知道怎么做，不等于知道本项目应该何时采用，也不保证未经提醒就主动执行。因此删去通用操作教程，但保留并补充关键节点的选择提示、默认策略和例外。首次选择形成工程约定，日常执行、事实变化重评，权限内不逐项审批。细则多不等于专业性，过度裁剪导致没有行为激活或交付闭环同样不是优化。

## 2. 三层对象，而不是全局阶段锁

项目维护长期目标、约束与路线；交付维护一次有边界的承诺和接收条件；工作单元维护认领、依赖、执行和交接。迭代是组织节奏，不强制等于发布版本。

保留 INIT / DESIGN / TEST_INFRA / DEVELOP / SYSTEM_TEST / RELEASE 名称，作为交付责任与关口的导航。默认按因果依赖推进，可满足局部前提后重叠执行；下一版本设计与当前版本验收分别跟踪，局部故障只重开受影响条件。允许工作重叠不代表可省略关口。

生命周期的完备性在于：目标和范围可识别、共享契约可依赖、必要工程能力可用、实现真实集成、候选满足验收、交给消费者后有接收与支持责任、反馈有处置。不能靠目录齐全或阶段标签宣称这些已成立。

## 3. 不变式

- 意图与权限不冒用：来源与授权范围清楚，Agent 自写记录不产生权限。
- 承诺不静默变化：输入、讨论、采纳、排期与执行有可辨效力。
- 当前知识有权威归属：入口引用，现行规则连贯，重大历史可追溯。
- 变更传到消费者：工作、文档、接口、门禁与证据受影响时有处置。
- 声明与成果相称：实现、验证、接受、交付、健康分别有依据。
- 中断可恢复：保留责任、工作位置、有效成果、决定边界与下一步。

裁剪允许改变载体和流程深度，不取消这些保证。项目事实变化后可重新判断适用性，不把初始化档案变成不可修订的永久决定。

## 4. 决策与评审

现版问题不是 Agent 永久身份固定，而是将决策权限过度绑定阶段末仪式。改为分开判断需求确认、技术可接受性和执行授权，按事项、影响、既有委托分配责任。

对话可形成有效决定。核对来源、对象、边界、条件及变化后复用，只问缺口，不重复同义批准；但方案认可不能外推费用、生产或数据操作。重要许可跨会话需有忠实摘要与来源，不伪造签名。平台限制仍有效。

独立评审仍适用于重要风险，rubric 也可有价值；不能以格式或发现数量代替实质判断。阻塞需要要求/风险锚点、证据或可信推理、影响与关闭条件；合理取舍可接受，偏好非阻塞。复审聚焦原问题及修订影响，新重大证据仍能重开；超预算不自动放行。

运行细则：[决策、变更与评审](<../skills/devloop/references/decisions-and-change.md>)。

## 5. 文档是共享知识，不是转储

知识按目标、需求验收、架构接口、工作实现、决定证据分层。借鉴受控工程表达思想，而不声称符合 ASD-STE100；术语明确、语句效力清楚，不要求机械句长。

需求记录可观察行为，不罗列局部变量与 helper；公开接口字段、配置键等真正契约应准确。现行 Spec/AC/接口和计划可受控修订，形成连贯当前版本。Git、决定与结果记录保存历史，不要求新读者拼接多轮补丁。

共同编辑需依赖基线、编辑范围和整合责任，合并检查语义不只是文本冲突。必要指引必须进入安装后常驻文档，不能仅藏在将被删除的模板注释里。

运行细则：[文档协作](<../skills/devloop/references/documentation.md>)；字段与归属：[记录约定](<../skills/devloop/references/records.md>)。

## 6. 变化、进度与恢复

新消息是项目输入，不总是当前最高优先任务。Agent 应对照当前承诺，必要时说明累计范围与返工影响，推荐本轮、替换、下轮、探索或暂停。用户明确改向后执行，同时维护原承诺处置、相关基线、工作和证据；不能用流程否决合法转向，也不能无声接单。

进度以项目导航、交付承诺和工作事实分层，执行状态与结果分开。重要变化和交接落盘，不逐命令记日志。中断先只读核查原执行者、任务和工作区，明确安全接管后才重验；不能自动删除未提交成果。

工作可按模块、纵切片、风险或集成职责拆分。并行隔离仅是起点，还需认领、依赖、通知、等待、整合和接管责任。分支策略沿用原生实践；无策略时以主干＋短期工作分支为默认，有真实多版本或发布维护需要再引入长期集成/发布分支。动手前主动选择分支、基线和隔离，不以“模型会 Git”省略判断，也不恢复 Gitflow 强制。

## 7. 验证、验收与实际交付

开发中尽早连接真实关键路径，风险定向验证可以前置。准备能力按本轮需要增量建设，关键门禁应自证能识别错误，不要求每项工具单独 ADR。

证据绑定要求、候选、修订、方法、环境和结果；按变化影响复用或重验，不把测试层固定在某阶段。分支绿灯不能拼成未运行的集成结果。

验收面向真实消费对象；源码测试不代替安装包/部署服务/构建产物验证。技术评审、测试、验收接受与执行许可分开，但可在有足够上下文的一次明确决定中共同形成。接受风险不能把 FAIL 改成 PASS。

交付对象与已接受对象保持一致，变化有差额验证。观察、恢复和支持责任按项目适用；不可逆迁移不能机械回滚旧代码。项目关闭、转向、弃用和下一轮同样保留承诺处置，而非永远自动回 DESIGN。

运行细则：[工作、进度与交付](<../skills/devloop/references/work-and-delivery.md>)。

## 8. 安装与升级

新项目安装建立入口、常驻规则、初始交付和必要载体；已有项目原地映射，不全量套模板、不重置到 DESIGN。导入时区分已确认要求、观察现状和未知理由，不从代码反推虚构 accepted ADR。

升级保留 ID、历史与有效成果，映射旧状态不能自动推断成功或认证授权。仓库实现变化不等于已安装副本和外部项目自动升级。

运行细则：[INIT](<../skills/devloop/references/phase-init.md>)、[迁移](<../skills/devloop/references/migration.md>)。

## 9. 验证与能力边界

技能产品只依赖自身入口、引用和模板，不依赖开发草案。安装后执行者无需加载完整 skill，也须通过常驻规则知道新输入、授权、文档、变更与恢复的最低义务。

采用静态引用/字段检查、隔离项目接入和 Agent 场景实验分别验证结构与行为，记录模型/快照、输入、输出与副作用。有限隔离实验不构成所有模型、复杂生产项目或长时程无人运行的保证。后续自动化只承担可确定检查，不用正则认定授权和业务验收。
