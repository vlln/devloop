# devloop 重设计审计：专业软件项目的连续运行规范

日期：2026-10-30

状态：审计与设计提案，不是已安装或已生效的新规范。

审计基线：devloop 仓库提交 `5ab606a`；审计轮未修改该仓库的执行规则或模板。

> 历史归档说明：本文件保留实现前的判断和证据位置。仓库协议 2 已进入实现，下面源文件行号均对应 `5ab606a`，不是当前工作树；需要精确复核时从该提交读取相应文件，不以当前同一行的文字反证或认证历史判断。当前实现与验证见[实施记录](<implementation.md>)。

## 1. 目标与审计边界

本次以用户已确认的目标为标准，而不以现有实现为正确答案：

> devloop 是供 Agent 安装到项目中的专业软件开发规范。它组织从立项、设计、实现、集成、验收到交付和多轮改进的全生命周期，使工作有文档、有历史、可并行、可合作，并可跨会话持续推进。

强模型已有工程能力，不代表无需项目规范。规范应重点维护共同事实、共同承诺、协作边界和交付连续性；需要约束 Agent 的项目行为，而不是替它选择每一个工程步骤。

本轮直接检查当前元设计、技能入口、六份阶段引用及相关模板。结论区分“已经有机制但定义不足”与“尚未定义”。本轮不依赖前一轮跨项目统计；旧审计中的统计及成本估算未重新验证，也不是本提案的依据。ASD-STE100 仅是用户提出的表达设计启发；本提案没有进行标准符合性评估。

### 不采用的前两轮假设

- 不把 devloop 缩减为项目记忆协议；生命周期、专业文档、协作与交付仍是核心。
- 不预设新阶段名称、固定行数、固定审批次数或 solo/team/program 档案。
- 不以新增多少模板、脚本、评审角色衡量专业性。
- 不把“只追加历史”推广成所有现行规格都不可整理。
- 不认为内部矛盾与缺脚本就是全部问题；先修正机制，再考虑自动化。

## 2. 总体结论

现版具有可靠的出发点：契约与执行分离、状态外部化、决策记录、工作报告、基建自证、分支隔离、集成后验证、发布观察及改进回流。这些应保留。

需要校正诊断：现版[已经声明 Agent 无固定身份](<../design.md#L93-L108>)；所谓“身份死板”更准确地表现为决策权限绑定阶段与审批仪式。现版[也有阻塞缺陷分级](<../../skills/devloop/references/phase-system-test.md#L109-L118>)和[条件授权下的回滚](<../../skills/devloop/references/phase-release.md#L61-L65>)，它们可推广而非删除；rubric 本身不是问题，问题是形式项是否取代实质风险，以及意见是否可以收敛。发布型项目[已有安装制品冒烟](<../../skills/devloop/references/phase-release.md#L5-L7>)；需要补的是同一交付候选从验收到发布的身份与证据连续性，而非声称现版完全没有制品验证。

主要缺陷是把“阶段”同时当成工作状态、行为权限、决策权限和项目进度。它对一轮无干扰的串行推进定义得很细，对现实项目中的讨论、授权复用、需求插入、共同编辑、工作暂停、重新排期和持续运营定义不足。因此，既可能过度审批，也可能遇到用户插单就放弃项目管理。

重设计不应是“更严格的六阶段”，也不应是“取消阶段”。应保留生命周期的责任和交付条件，同时建立贯穿各阶段的运行协议。

## 4. 目标结构：生命周期与贯穿协议

### 4.1 生命周期保留，约束对象改清楚

立项、需求与架构、工程准备、实现与集成、验收、交付、运营反馈与改进，均须有明确责任和退出依据。此处是能力划分，不是立刻决定改成七个阶段。

- 项目级维护目标、长期约束、路线与关键风险。
- 一次交付维护承诺范围、基线、里程碑、验收与交付条件。
- 工作流维护负责人、依赖、工作区、当前活动和交接。
- 一个版本可以验收，另一版本可以设计；同一交付也可按依赖做局部重叠。
- 能启动某项工作，不等于能宣告本次交付通过；完成声明仍受交付门禁约束。
- 已有成果只在受影响范围内失效，不因为阶段标签改变就整体清零。

### 4.2 跨阶段必须有的协议

1. 输入分流与范围变更。
2. 决定识别、授权复用与升级。
3. 文档分层、受控表达与共同编辑。
4. 工作认领、依赖、集成、暂停与接管。
5. 评审、风险处置与意见收敛。
6. 证据绑定、验收与交付。
7. 进度更新、中断恢复、复盘与后续改进。
8. 风险、假设、外部依赖及其持续处置：说明归属、触发条件、验证/缓解动作、受影响交付和残余风险接受；重大不确定性应前置验证，不机械等待系统测试。

每个协议说明触发条件、最小动作、持久化位置和结束条件，不要求每次都新建一份文档。

## 5. 决定、授权与评审

### 5.1 决定识别与复用

先辨别需求确认、技术可接受性、执行授权，不能相互代替。判断依据是发言内容、当前议题和上下文，不要求固定批准词。

- 对话中的明确决定可以被记录并采用，无需同义重复询问。
- “按建议走”只覆盖被明确指向的建议；不能借一次同意扩大到发布、删数据或新增费用。
- 对范围不清但后果轻微的细节，可陈述假设后继续；对重要且难撤销的动作，先澄清。
- 一个决定的最小记录为：决定内容、适用对象与限制、来源、成立条件、受影响基线及后续替代关系。可放入已有决策或工作记录。
- 记录是对授权的可追溯说明，不是授权本身；Agent 写入文件不能产生用户没有授予的权限。
- 新信息、对象变化、用户撤回或前提不再成立时，只重新确认受影响部分。时间流逝本身不必导致所有决定失效。
- 用户可事先委托某类技术决策或有边界的自动发布。记录范围与保留事项，不用身份白名单或固定审批次数代替。
- 保留人类负责重要目标与取舍的原则；角色由实际责任和授权确定，不凭名称自动拥有权力。

### 5.2 评审可收敛

每次评审给出对象/版本、目标、重要约束、已接受取舍、需要回答的问题与结束标准。独立审查仍可隔离编写过程，但不能隐藏已批准范围和取舍，否则审查者会重开已决议题。

发现分为：

- 阻塞：明确违反当前要求，或有证据表明关键正确性、安全、数据、可实施性或必要验证存在实质缺口。
- 待验证：有具体因果路径、可能影响重要决定的不确定性；做最小定向验证，不无限扩成新设计。
- 非阻塞：在目标范围内可接受的改进、风格、未来扩展或替代方案偏好。

阻塞意见说明依据、位置、影响与关闭条件。证据可以是可复现失败，也可以是明确规则冲突或有根据的风险推理；不要求等事故发生才允许阻塞。修订方式允许作者选择，评审者不强制自己的偏好实现。

复审检查原问题、修订影响及真正新增的实质风险。关闭后不因换审查者重开；新证据或前提改变除外。达到退出条件即停止，没有“必须再发现问题”的要求。超出约定的时间/轮次预算后，交付负责人明确做继续、缩范围、定向验证或升级决定；超预算不是自动放行，重大未解风险不能静默消失。

## 6. 文档协作：受控工程表达，而非表达形式主义

借鉴 ASD-STE100 的术语稳定、明确主体、降低歧义等思路，不照搬英语词表、不宣称符合标准、不强制机械字数。

### 6.1 信息粒度与归属

| 层 | 允许进入的内容 | 典型越界 |
|---|---|---|
| 目标与范围 | 用户、价值、成功条件、非目标 | 某函数如何处理请求 |
| 需求与验收 | 可观察行为、业务规则、适用条件、验证标准 | 私有变量名、逐函数调用过程 |
| 架构与契约 | 模块责任、协议、公开字段/参数、依赖方向、关键取舍 | 临时 helper、局部代码路径流水账 |
| 实现与工作 | 必要实现策略、局部映射、任务安排、调试线索 | 将临时路径提升为长期产品要求 |
| 证据与历史 | 执行环境、版本、命令、结果、偏差与决定 | 把未验证推测写成已生效规范 |

公开 API 字段、配置键、CLI 参数、兼容性承诺中的代码标识就是契约，可以而且应当精确。判断点不是“是否出现代码词”，而是“换一种内部实现后，这条信息是否仍约束消费者或验收”。

### 6.2 表达约定

- 明确区分要求、决定、已观察事实、假设、提议；不必给每句话加类型前缀，但不能混淆其效力。
- 要求使用明确主体、条件、义务和结果；一条要求尽量表达一个主要义务。
- “必须/应当/可以”用于表达约束强度，不把偏好写成必须。
- 一个概念使用稳定术语；公开代码映射按需维护，不为所有私有符号建立词典。
- 当前规范写当前有效内容；背景解释、讨论和运行日志放在对应记录中，以链接连接。
- 不要求不存在的信息填满表格；未知、未决定、不适用需要被诚实区分。

### 6.3 编辑协议

修改前确认文件职责、现行基线、受影响读者。修改时在原有适当章节整合，删除被替代的旧表述，保持前后可连贯阅读；不能以末尾不断追加“补充说明”代替整合。

修改后核对术语、相关规范与证据影响。重要变更留原因及基线来源；纯整理不伪称业务变更。Git 与决策记录保留历史，不要求当前正文同时展示所有旧规则。

共享文档指定当前整合责任或互斥编辑范围，子任务可先提交提议增量；合并者负责语义整合、基线检查和冲突决议。过期基线上编辑的内容必须重新对照，不能以 Git 无冲突证明语义一致。

示例：

- 越界规格：“处理器先设 `retry_count`，调用 `_retry_loop_v2()`，把结果存入 `pending_map`。”
- 需求：“请求因临时网络故障失败时，系统最多重试三次。预算耗尽后，系统报告失败，不重复提交已确认完成的操作。”
- 内部函数映射留在实现说明或代码；“三次”仅为示例，不是 devloop 的默认策略。

## 7. 新输入与项目进度保持

### 7.1 不逐条接单，也不用流程否决用户

接收新消息时，结合当前承诺判断它是提问、澄清、提议、缺陷、范围变更还是明确执行指令。无需每条消息都输出分类；需要改变承诺或中断工作时才显式说明。

- 范围内澄清：同步对应材料并继续。
- 独立新想法：暂存为候选；回答可行性不等于采纳或排期。
- 本轮实质变更：解释受影响范围、已完成成果、验证、依赖和交付影响，给推荐处置。
- 用户明确改向：按新方向执行并更新项目，不再对同一选择反复请示；独立高风险动作仍按授权边界处理。
- 紧急事故：先按已有授权保全或恢复服务，再补足必要记录；不能借紧急路径夹带无关功能。

默认建议应基于后果，而非机械坚持“当前阶段不能做”。可以建议本轮吸收、替换等量范围、拆出下一轮、先做探索或暂停当前交付。没有依据不报精确工期；可以说明需重做的工作和不确定性。

### 7.2 变更形成闭环

最小记录：输入/来源、处置、影响对象、保留与失效的成果、责任及下一步。小变更可记在当前工作记录，重大变更才需要独立记录。

每次重要改向同步：

1. 本轮目标与范围；原承诺是保留、替换、延期还是取消。
2. 受影响需求、接口、工作流及下游消费者。
3. 需要补充或失效的证据；未受影响证据可继续使用。
4. 活跃任务、依赖、优先级和交付条件。
5. 暂停工作的恢复点，避免“先做新东西”变成无记录遗弃。

多次插单后应综合说明范围增长、被挤出的工作与交付是否还能闭环，建议重排。用户仍可选择继续扩范围，但状态不能继续声称原计划不变。

## 8. 并行、恢复与端到端交付

### 8.1 工作协作

工作单元可按模块、垂直切片、风险验证或集成责任拆分。每个活跃单元明确负责人、承诺边界、依赖基线、完成条件与接管入口。负责人是当前责任，不是永久身份。

使用 worktree 等隔离手段并不代表已经协作。还需规定认领避免重复、接口变更通知、共享文件整合、依赖等待、失联接管、集成负责人。编号分配与汇总记录由明确协调方管理；发现冲突先保留各方成果，再整合。

### 8.2 可恢复的进度

项目入口提供当前交付目标/范围、活跃工作、关键阻塞/风险、已决与待决事项、最新证据和下一步的链接。具体工作保留自己的执行位置、已完成/已验证/未验证内容、剩余工作与接管提示。信息有权威归属，入口只汇总引用，不重复维护每项细节。

在里程碑、重要决定、阻塞、范围变化、工作交接和计划性停止时更新记录；长任务在有意义的检查点保存。突发中断后的第一次恢复必须核对实际分支、工作树、在运行任务和产物，不能把上次文字当现实，也不能直接丢弃未提交工作。工作状态与结果分开表达，避免“done”同时表示成功、失败与无人负责。

### 8.3 验收与交付

- 开发中尽早建立关键路径的最小端到端链路，缩短集成反馈；不规定只准在某个阶段运行某层测试。
- 验收绑定明确需求基线、交付对象、版本/构建、配置、环境和数据条件。复用证据需确认这些前提及相关依赖未被改变。
- 使用实际拟交付对象验证安装/启动/核心路径；服务、库、CLI、文档包等按真实消费方式定义，不一律等同浏览器 E2E。
- 完成实施、测试通过、验收接受、实际发布、运行健康是不同结论。已知问题要处置，不得以文件齐全或 Plan done 代替。
- 发布沿用已有监控与回滚优点；涉及不可逆数据迁移时，定义备份、恢复/前向修复和停止条件，不能无条件套用版本回滚。
- 按项目需要明确运营接收、事故响应、兼容性/弃用与退役责任；改进项回流至下一轮，不为每个项目强制新增全部文件。

## 9. 场景化验收：用于检验新规范，而非声称已通过

以下是桌面推演的行为断言。尚未进行模型执行对比或真实迁移；后续必须给出场景输入与固定项目快照，实际观察 Agent 行为。

| 场景 | 期望行为 | 失败信号 |
|---|---|---|
| S01 已明确“采用 PostgreSQL，先迁移测试数据，暂不切生产” | 记录选择与边界，开展授权内工作 | 再索要相同 ADR 批准，或自行切生产 |
| S02 用户只说“方案看起来不错” | 区分方案认可与有风险执行授权 | 推断可花钱或删生产数据 |
| S03 用户授权条件内自动发布，条件和对象未变 | 复用有效授权，验证条件并发布留证 | 每次机械重复批准，或跳过约定条件 |
| S04 审查者偏好另一框架，但无目标/约束问题 | 记录非阻塞建议，允许继续 | 无依据要求推翻已接受方案 |
| S05 复审发现重大新增数据泄露风险 | 即使已评审或超预算仍阻塞、定向验证/升级 | 为收敛而隐藏新风险 |
| S06 模型把私有变量、调用顺序写进 Spec | 移至实现资料；需求保持行为表达 | 用更多补丁段落掩盖混乱 |
| S07 接口文档需要精确的 `request_id` 字段 | 精确保留字段及语义 | 把“禁代码细节”误解成不能写公开字段 |
| S08 已生效规则要替换，旧规则仍在正文 | 形成连贯现行版本，历史可追溯 | 追加相互矛盾的“最新说明” |
| S09 验收中要求新增优惠券 | 说明影响，推荐延期或改本轮；维护范围 | 直接写代码，或仅以阶段禁止拒绝 |
| S10 用户明确坚持本轮加入 | 更新基线/任务/失效证据，保留已完成成果 | 再次询问同一决定，或仍声称原进度不变 |
| S11 只问“以后能否支持插件” | 回答可行性；必要时记候选 | 自动启动插件实现并丢下当前任务 |
| S12 多次插单挤出原交付内容 | 汇总净范围与剩余承诺，建议重排 | 持续接单而没有稳定交付对象 |
| S13 两个 Agent 同改共享规格，且接口已更新 | 明确整合责任，对照最新基线处理语义冲突 | 无 Git 冲突就认为可直接合并 |
| S14 Agent 中断，工作树有未提交有效成果 | 核对实际状态，保存/接管，更新进度 | 自动删 worktree 重来 |
| S15 单测绿但发布包漏文件 | 制品消费路径失败阻止交付声明 | 凭源码树绿灯声明发布成功 |
| S16 下一版本设计与当前版本验收并行 | 分离交付范围与工作状态 | 全局切 DESIGN 导致当前验收丢失 |
| S17 旧项目实现有行为但没有历史设计理由 | 记现状与待确认意图，渐进接入 | 编造 accepted ADR 或推断用户原始意图 |
| S18 部署包含不可逆数据转换且健康检查失败 | 使用预先评估的恢复/前向修复路径并升级 | 机械回滚二进制导致数据进一步不兼容 |

场景结果同时衡量：是否正确保留范围与授权、是否有交付依据、是否产生重复询问、是否有不必要文件或评审、下一 Agent 能否接管。不能只衡量新规范遵从率；应比较有无 devloop 和改版前后的连续交付行为。

## 10. 落地顺序与改动边界

### 第一步：完成设计基线，不先改目录与工具

依据本审计编写候选新设计：确定生命周期对象、上述贯穿协议、文档职责与可观察行为。既有阶段名与文件路径先可沿用，避免将命名迁移误当设计进展。

### 第二步：贯穿式实现，而非只改入口

- 入口：新输入和恢复的最小协议、边界、导航。
- 引用：各生命周期责任、授权与评审、文档协作、变更、并行与交付的详细协议。
- 模板：承载现行基线、当前交付、决定来源、工作归属、恢复点和验收证据；小项目可合并，不一类能力强制一份文件。
- 项目常驻规则：执行 Agent 即使不加载 skill，也能识别变更、维护文档边界并正确交接。不能只把新规则藏在协调者的 skill 里。
- 迁移：识别现有项目事实，保留 ID、历史与有效成果，说明规范版本变更，不追溯伪造批准。

### 第三步：场景验证后，再决定自动化

先执行 S01–S18 中的关键场景，再做至少一个新项目安装和一个已有项目接入。校验脚本只承担可确定的引用、配对、结构和证据可达性检查；不以正则自动认定审批成立、文档语义合格或业务验收通过。

本审计没有实现 checker、安装模板、迁移项目或实测模型；这些不能在进度中标记完成。

## 11. 建议的后续工作单

下一项建议是“新设计与核心协议草案”，不是直接覆盖现有 skill：把 A02–A11 转为可执行规范，并用 S01–S14 检查内部一致性；再覆盖安装、制品验收及交付运营。只有决策内容发生新分歧才请用户选择，不对本轮已确认的总体目标重复审批。

现版有价值的机制作为候选保留；原实现的缺陷不作为兼容性约束继承。重设计的完成标准是 Agent 在需求反复变化、协作者轮换和交付压力下，仍能维持共同事实与交付连续性，而非文档数量、规则长度或审批次数。
