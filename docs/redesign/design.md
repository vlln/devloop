# 候选设计基线

状态：draft。职责与阅读路径见[入口](<README.md>)。

## 1. 目标和边界

### 1.1 必须支持的项目形态

Agent 能将项目接入一套专业开发规范，维护从立项、需求与架构、工程准备、实现与集成，到验收、交付、运行反馈与多轮改进的连续工作。人、Agent、不同会话和并行工作者可以凭项目资料协作，不依赖某个执行者的完整聊天历史。

专业性由共同承诺、责任、影响传播和交付依据体现，不由文件数量、固定角色层数、审批次数或指定开发方法体现。

### 1.2 非目标

- 不教授通用编码、测试、Git 或项目管理基础。
- 不要求模型按固定章节、固定测试顺序或逐文档串行完成所有工作。
- 不将工程流程用于否决用户合法改变目标；流程负责显式管理改变的后果。
- 不以通过格式检查代替语义评审、风险判断、业务验收或执行授权。
- 不提供一个外部调度系统。Agent 能自协调；可用的平台任务、PR、分支和日志作为载体，但不假定它们一定存在。

## 2. 对象与术语

| 对象 | 定义 | 主要维护内容 |
|---|---|---|
| 项目 | 有持续目标与约束的软件工作整体 | 用户/价值、成功条件、非目标、路线、重要风险、协作与授权约定 |
| 交付 | 一次有边界的承诺及其接收对象，可覆盖多个工作单元 | 范围、基线、里程碑、验收与交付条件、当前状态 |
| 工作单元 | 可被认领、执行、交接和集成的工作 | 责任、依赖、计划、工作区、证据、结果与下一步 |
| 基线 | 在某一范围内共同依赖的已采纳要求、接口、决定及版本/修订标识 | 哪些内容有效、由谁消费、何时替代 |
| 决定 | 对需求、取舍或安排的明确采纳 | 内容、来源、边界、成立条件和替代关系 |
| 授权 | 允许在给定范围和条件内实施某类动作 | 对象、环境、限制、条件和保留事项 |
| 证据 | 支撑某项判断的可定位观察、测试、审查或运行结果 | 对象、基线、方法、环境、结果与适用性 |

迭代是组织下一次工作和学习的节奏，不强制等于发布版本，也不强制每次迭代都生产部署。一个交付可跨多个迭代；一次迭代也可完成多个独立交付。大型项目可用子项目或交付依赖表达跨仓库工作，不预设额外管理层级。

## 3. 系统不变式

1. **意图与权限不冒用。** 目标及其重大取舍来自用户或实际有权者；Agent 只在现有授权内决策与执行。文件状态和角色名不产生权限。
2. **承诺不静默变化。** 讨论、采纳、排期和执行可以合并发生，但必须可区分。改变交付范围要更新相关工作与判断依据。
3. **现行事实可定位。** 重要信息有明确权威归属；汇总入口只引用或注明来源，不形成互不一致的平行真相。
4. **变更传到消费者。** 共享基线改变时，受影响工作、文档、接口、门禁与证据获得明确处置。
5. **成果与声明相称。** 实现完成、验证通过、验收接受、已交付和运行健康分别有依据；未完成与未验证不会被状态名掩盖。
6. **中断不使项目失忆。** 重大决定、工作归属、已完成与待验证成果、恢复点和下一步能够从项目持久化资料恢复。
7. **历史不被静默改写。** 当前知识可以整理和修订，但重要原承诺、决定和已发生结果仍可追溯；纠错明确标注，不伪造当时依据。

## 4. 生命周期：约束一次交付，不锁死整个项目

以下是责任领域与关口，暂不强制更换现有阶段名称。一个交付默认按因果依赖推进；工作可在满足局部前提后重叠，完成关口不能凭重叠执行而省略。

| 责任领域 | 启动所需前提 | 离开该关口必须成立 | 典型承载 |
|---|---|---|---|
| 立项与交付界定 | 有用户目标或需要评估的问题 | 用户/价值、成功条件、初始范围与非目标、重要假设与责任明确；未知项有处置 | 项目愿景、交付计划 |
| 需求与架构 | 目标及范围足以指导分析 | 本次承诺可验收；共享边界和关键取舍足以让相关工作依赖；重大未知已验证或明确隔离 | Spec、AC、接口、ADR |
| 工程准备 | 已知首批工作与验证需要 | 对即将执行的范围，构建、验证、隔离、环境和交付路径可用；关键门禁能识别错误 | 工程配置、准备工作报告 |
| 实现与集成 | 依赖的基线和必要能力可用；未定项有明确隔离 | 本交付承诺的实现已集成，受影响验证有依据；已知偏差已处置 | 计划、代码、测试、工作报告 |
| 验收 | 有明确候选对象、要求基线与验证条件 | 核心承诺和适用非功能要求已核验；偏差与风险由有权者接受或阻塞 | 验收汇总、证据引用 |
| 交付与接收 | 候选已接受，必要操作在授权范围内 | 同一候选或经影响评估的等价对象已交给实际消费者；部署/安装、观察与恢复责任明确 | 发布/接收记录、用户与运维资料 |
| 反馈与下一轮 | 有可用成果、问题或学习结果 | 问题和经验有处置；交付关闭或转入支持；候选改进不会自动成为下一轮承诺 | backlog、复盘、事故记录 |

重要约束：

- 架构探索可需要代码；不能因“仍在设计”禁止必要实验。实验不自动取得生产实现的地位。
- 工程准备为当前需要服务，不要求全部未来能力一次搭完；已有能力以有效证据复用。
- 开发中可以运行系统、性能、安全或集成验证；正式验收仍需覆盖最后候选及相关风险。
- 某工作需要重设计或修基建，不等于其他无关工作全部倒退；记录受影响交付的未满足条件。
- 当前版本验收与下一版本设计分别属于不同交付；它们共享资料时必须标明现行与候选适用范围。
- 发布是有外部效应的一类交付，不是所有项目的唯一出口；库、CLI、内部服务、研究原型和规范包按真实消费方式接收。

## 5. 跨阶段运行机制

运行行为分别由以下协议定义，阶段说明只引用，不复制：

- [决策与变更](<decisions-and-change.md>)：识别新输入、复用已有决定、调整交付承诺、评审与升级。
- [文档协作](<documentation.md>)：知识归属、受控工程表达、现行基线和历史、共享编辑。
- [工作与交付](<work-and-delivery.md>)：认领、进度、风险、依赖、集成、恢复、验收和运营接收。

项目常驻规则必须包含这些协议的最小行为入口。只把协议放在协调者加载的 skill 内，无法约束不加载 skill 的执行 Agent，不算完成安装。

## 6. 记录与载体

默认沿用已有文档类型和项目工具；缺少的记录可先作为现有文件中的章节，不强制每种机制一份文件。

| 信息 | 默认权威归属 | 边界 |
|---|---|---|
| 项目目的与约束 | 项目愿景/说明 | 不混入每次实现和运行细节 |
| 一次交付承诺、进度与变化 | 交付计划或现有计划索引 | 与工作执行事实分开，允许显式重新基线 |
| 需求、验收条件、接口 | Spec、AC、接口定义 | 稳定 ID，区分当前与候选适用范围 |
| 重要技术取舍 | ADR | 技术决定不是生产操作许可 |
| 决定/授权摘要 | 就近的决策、交付或工作记录 | 一个权威记录，引用来源；不复制整段聊天 |
| 单元工作与结果 | Plan/Report 或项目原生任务 | 计划可修订，结果可追溯；不能将失败等同交付完成 |
| 候选、待澄清与以后工作 | backlog 或明确候选区 | 只有需要持续跟踪的想法才登记；不把每个提问变待办 |
| 验收、交付、运营与改进结果 | 汇总 Report、发布/接收与复盘记录 | 明确对象与责任，引用既有证据 |
| 总览与接管导航 | 项目入口及文档索引 | 汇总当前交付与活跃工作的权威链接 |

基线可以是 Git 提交配合对象 ID/修订，而不要求每类文档都新造整数版本。工具或聊天来源不能长期访问时，保存足以识别意思和限制的忠实摘要，不编造消息编号、签名或批准身份。

## 7. 裁剪、安装与既有项目接入

### 7.1 裁剪

安装时按交付对象、并行方式、外部效应、数据与合规风险选择必要能力，记录显著适用/不适用与依据。默认使用项目原生分支、评审和任务工具；没有既有策略时，可用 Gitflow 与 worktree 作为起点。

裁剪不允许取消不变式。无适用对象的机制不强行制造，例如无服务部署不需要生产监控。适用性随项目事实变化可更新，并传播影响；不能以一次初始化永久禁止重新判断。

### 7.2 新项目

1. 明确项目目标、初始交付和责任/授权边界；不要求用户先阅读整套规范。
2. 建立入口、文档职责、工作与历史载体，形成首轮承诺和待决问题。
3. 按最早工作需要搭建工程能力并推进生命周期；模板内容不是就绪证据。
4. 检验接手者能定位当前目标、决定、活跃工作和下一步，不能只验证目录存在。

### 7.3 已有项目

1. 读取原生规范、版本/分支、需求、在途工作与可用证据，不先覆盖布局。
2. 将导入内容区分为已确认要求、观察到的现状、未知原因与待确认意图。依赖配置只证明使用现状，测试只证明覆盖到的行为。
3. 识别正在进行的交付和未满足条件，不因接入而一律重置 DESIGN。
4. 对不足建立增量工作；保留 ID、成果和有效授权，不补造历史批准或选型理由。
5. 在项目入口标明适用的规范版本和接入范围，执行前核对重要授权；不因旧文件里写了 approved 就假设有效。

## 8. 实现与验证边界

本轮交付是候选设计，不是 skill 升级。后续实现依次覆盖入口、详细协议、阶段引用、常驻规则、模板和迁移说明，避免新旧义务互相矛盾。

[场景检查](<scenarios.md>)是行为验收依据。先做静态一致性检查，后用固定项目快照执行 Agent 场景，记录实际输出和副作用；再检验新项目安装、既有项目接入与至少一次多轮改进。格式 checker 仅处理可确定结构，不推断授权或验收成立。

不能因为本设计经审阅就宣称运行效果已证实。是否需要进一步工具化，依据实验暴露的重复失误与可确定约束决定。
